# Realtime update implementation, inactive stage

This document describes the server contract. For exact deployment effects, sequence and rollback, see realtime-activation.md. Source includes guarded public-entry routes, runtime wiring and scheduled drain handling, but current wrangler configuration adds no realtime binding or new cron.0037will apply remotely through normalCI when this stage merges. No app client is included.

## Mounted facts (verified against auth-only-worker.js and identity-runtime.js)
- Mounted reads: GET /v1/manage/session, entries, active-codes, unassigned, sources.
- Mounted code-visibility writers: assignment intent finish, device logout/revoke, recovery controls (security generation bump), personal organization (viewer-only).
- Not mounted, no caller: entry management (create, share, revoke, delete, revokeSource) and SourceEntryStore.receive. Their triggers are contract-tested, so they emit once mounted.

## Design
- The stream is content-free: `{"v":1,"t":"changed"}`, plus close messages. Clients refetch through the existing authorized GETs.
- D1 triggers write realtime_outbox rows inside the same statement/batch as the change (rollback, replay and cascade tested on SQLite and local workerd D1). Hint sources: code insert/assign/live-delete, share insert/update, entry insert/update/delete, source insert/revoke, personal organization, device revoke, security generation bump.
- Entry delete and source revoke capture former recipients at write time as packed snapshot rows (kind `accounts`, at most 100 distinct sorted ids per row, N/100 rows, no LIMIT, nothing dropped). This bounds row and payload size and cuts write multiplication. It does NOT bound total trigger work: the capture and the cascade are still O(recipients) inside one D1 statement. Workerd D1 measurement: deleting an entry with 1037 recipients wrote 1079 rows (11 packed rows plus owner row, share cascade, entry).
- Combined invocation budget. Free allows 50 subrequests and 10 ms CPU per request or cron invocation (https://developers.cloudflare.com/workers/platform/limits/), and D1 states 50 queries per invocation (https://developers.cloudflare.com/d1/platform/limits/, db.batch counts once). The docs do not say whether D1 queries and Durable Object stub calls share one bucket, so they are treated as sharing: measured D1 queries plus hub calls never exceed `COMBINED_CEILING` = 45, leaving 5 for setup, handler work after the snapshot and network overhead. Post-write drain (only after a route-allowlisted 2xx write): at most 10 hub calls and D1 min(20, 35 - what the request used, over-counted under overlap); it does not start below 9 D1 queries. Cron `*/5 * * * *` (own invocation, only when REALTIME_HUB is bound): 20 D1 + 25 hub = 45. The existing `*/15` identity cleanup (about 33 statements) never drains. The drain never issues a query it cannot pay for and keeps one for the release that ends a claim. Exhaustion leaves the row due (cursor persisted), cron finishes it. Adding the `*/5` trigger is deploy-time work.
- Hub delivery accounting: every hub call (success or failure) is spent before it is made. A budget stop is not a failure: no attempt is counted, the claim is released, and the cursor (entry fanout, packed `accounts` rows; an empty-string cursor means the owner hint was already sent) is persisted in the same release statement. Failure isolation: work runs in chunks of up to 10 recipients; before each chunk one D1 query is PREPAID for the batch that would isolate its failures (refunded if nothing failed). A failed recipient becomes its own `account` row (attempts 1, next_attempt_at = now + 30 s, skipped if an unclaimed hint for that account already exists), and the parent cursor moves past the chunk, so an early poison recipient never starves later ones. That row then follows the normal exponential backoff and is dropped after 8 attempts. If the isolation write itself fails, the parent backs off as a whole and the cursor does not move. The entry owner hint goes through the same prepaid isolation as any recipient, and the empty-string cursor is set only after it was accepted or durably isolated. Side effect to know about: a fresh hint for that account coalesces into the backing-off row and is delayed until its next attempt (up to 15 minutes) while that recipient's hub keeps failing; reads still re-authorize.
- CPU: Free is 10 ms per invocation. Staging is small chunks with no per-recipient work beyond the hub call. Measured here (node, in-memory sqlite, stub deliver, so only a rough indication, not a production guarantee): about 6 ms wall for a 10-delivery foreground drain including JIT warmup. The plan is not raised; a drain that is cut short by CPU limits leaves the row claimed until the 60 s lease expires, then it is reclaimed.
- Residual unmetered work: the query meter counts the runtime database object only. D1 queries a handler issues from its own waitUntil after the foreground snapshot, and any D1 call outside the runtime db (auth-only worker setup), are not counted; the 5 units left under the 45 ceiling are the only cover for them. The meter is isolate-wide, so overlapping requests make a request's own use over-estimated, never under-estimated.
- Foreground relevance audit (every writer of device_sessions.revoked_at and account_security.generation, from exact source paths): drains after 2xx on POST /v1/manage/recovery/finish (session-revoke, passkey-revoke), POST /v1/manage/recovery/consume-change, POST /auth/recovery/email/complete-finish (generation bump), device logout, GET/POST /auth/login/complete (retires the prior browser session), assignment finish and organization PUT. Cron-only by design: Google sign-in (/auth/callback, /auth/google/continue/*, /auth/google/protection/*; it retires the prior browser session and the trigger still writes the row, but it adds a provider fetch and edge calls and no headroom is qualified, so no foreground drain and no Google ctx/realtime wiring is needed), refresh-token replay revoking a device inside /auth/restore (answers 303 or 401, no success signal) and the unexpected-child-no-op revoke in login completion. Delay is not an authorization gap: reads re-authorize every time. This audit is source reading plus unit tests of the allowlist, not a per-route runtime test.
- Socket lifetime: a delayed cron close is best effort only. A socket can never outlive its original access close_at alarm (5 minutes from ticket minting), so a late hint does not add ten minutes; the 6 minute activity window only decides which accounts are asked at all.
- Activation checklist (all held): migration 0037, the REALTIME_HUB DO binding and migration, the limiter bindings, the wrangler cron trigger `*/5 * * * *` (kept separate from `*/15`), and the client implementation of the contract above.
- Poison rows: attempts + next_attempt_at, indexed (next_attempt_at, seq), exponential backoff 30 s doubling to 15 min, drop after 8 failed attempts. Dropping is safe: hints carry no data, reconnect refetches, the 5 min socket cap backs up revocation closes, and data authorization stays in the GETs. Budget or page-limit stops are not failures.
- Client contract (not implemented here): 429/503 on ticket or upgrade means back off using Retry-After with jitter, never tight polling; 401 on ticket means the session is revoked or expired, so do NOT retry, require sign-in; an unexpected or expiry close means re-ticket only if the current session is still valid or renewable, and always fetch a fresh snapshot after connecting.
- (older) Delivery: bounded drain Claim by random claim_id (compare and set); every read, cursor advance, release and delete is guarded by that exact id; the lease clock only decides expiry. Entry-scoped recipients resolve at delivery time, 100 per page with a persistent cursor. At least once; failures stay for the next drain; cleanup eligibility after24h, bounded per run, not a hard maximum retention.
- Activity gating: minting a ticket records realtime_activity(account). A socket can only exist within 5 minutes of a mint (its close time is the access expiry), so delivery skips accounts with no ticket in the last 6 minutes, including revocation closes. No Durable Object is created for them. A client always fetches a snapshot after connecting, so a skipped hint cannot hide a change.
- Tickets: 30 s, one use, in Sec-WebSocket-Protocol, max 4 live per device, consumed by one guarded DELETE...RETURNING (device active, generation, method). The socket closes at the access expiry (5 min). NoOTP or message content is stored in theDO. Socket attachment/tag metadata includes device identifiers and expiry, and theDO is addressed by account identity.
- Hub: stores noOTP content or application records; socket metadata carries device identifiers/expiry; max 16 sockets, oldest replaced; alarm armed only for the earliest future expiry and cleared when none; revoke closes by device tag; generation bump closes all.
- Edge: the realtime paths exist on the public Worker only when `realtime:{edgeAddress,edgeGlobal}` is passed. They use their own limiter bindings and never the shared auth, read or address counters. Preflight is pure and exact (POST, Authorization only, app origin).

## Later activation work

Later stages add the wrangler SQLiteDO binding/class migration, dedicated limiter configuration, then five-minute cron, then app client. env.REALTIME_HUB drives the guarded drain; absent bindings keep routes404and drains inactive.
