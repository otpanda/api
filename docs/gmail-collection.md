# Gmail code collection (prepared, inactive)

## Trust model
- A message is collected because it arrived in the mailbox the owner connected, fetched from Google's API with that owner's own token. The push body is only a hint (mailbox and history id).
- The sender is NOT authenticated. No DKIM, SPF or Authentication-Results check is made, and provider headers are ignored. `from` is the From header as written. It is a match key for assignment rules and must never be shown as a verified service identity.
- Consequence, stated plainly: a forged From plus a code-looking number can reach an entry whose rule matches that sender (and anyone or any agent that entry is shared with), and can replace the useful latest code. Assignment and sharing rules are unchanged by this stage. Any decision to narrow them is a separate product choice.
- Authentication that stays: the Pub/Sub push is verified by Google OIDC (JWKS cache), the mailbox maps to its owner through the stored connection, and revoke/disconnect stop all work.

## Flow (push driven, no polling)
Gmail watch (INBOX) -> Pub/Sub push -> Worker. For one push: history.list from the stored cursor, fetch each new message once (`format=raw`), parse, extract, store. Handled ids are recorded, so replays and overlaps are safe. The cursor only moves over fully handled history records. If Google drops the history window (404), a bounded resumable one-day recovery runs across redeliveries.

## Bounds (engineering limits, not approved product policy)
| Limit | Value | Behavior |
| --- | --- | --- |
| Raw message | 512 KiB | larger: skipped, counted as `too_large`, shown as skipped |
| Raw request | 5 s abort and body deadline | timeout: message deferred, not dropped |
| MIME | depth 5, 40 parts, 256 KiB text | truncated, never unbounded |
| Per message cost | 8 subrequests reserved (measured 7) | the budget is checked before each message |
| Messages per invocation | `maxMessageUnits` (the runtime passes 1 for now) | stops with 503, Pub/Sub redelivers |

## Transient fetch failures (table `gmail_deferred`, migration 0051)
A fetch that times out, returns 5xx or 429 is queued instead of blocking the history behind it: id, first/last times, attempts and reason (`fetch_timeout|fetch_error`), no content. Backoff 1 min doubling to 1 h, no age limit. Other errors (for example 403) are not transient: the push answers 503 and the cursor holds, so Pub/Sub retries.
- Retries run after forward progress on a push (`drainDue`, 3 messages) and from `sync.drainDueAll()` for rows that are due. That cron touches only mailboxes that have a due retry. It does not scan inboxes.
- Cap 1000 pending per source, enforced inside the single insert. When full a new deferral throws: 503, cursor held, nothing evicted.
- Handled + dequeue is one batch. Revoke (trigger) and disconnect delete pending rows. Never pruned by the 8 day handled retention.
- Owner status: `store.deferredStatus(ownerId, sourceId)` and `ownerDeferredStatus(ownerId)`: counts and timestamps only. Skipped reasons are `too_large` and `invalid_message` (bad response or no From).

## Removed
mailauth, patch-package and the postinstall patch, the DoH resolver, the DKIM policy (signatures, lookups, key size, signature age), the 15 minute grace and the `unauthenticated` ingest rule. Plain `npm ci` and `npm ci --ignore-scripts` are now equivalent for this feature.

## Not done
Outlook stays disabled (`provider_disabled`). No watch, OAuth connection, ingest or cron is activated by this change.

## Label mode (optional, inactive)
Off unless a runtime passes `labelFilter` ({query, labelName}, see `src/gmail-label-filter.js`) to `GmailSync`. Without it everything above is unchanged: INBOX watch, `gmail.readonly` only, no mailbox setting is touched.

With it, connecting creates ONE label and ONE filter in the owner's own mailbox. The filter is add-label-only (criteria.query, action.addLabelIds=[label]; no archive, mark-read, forward or delete). The watch, history reads and one-day recovery then follow that label, so Gmail only wakes the Worker for mail the filter labeled.
- Consent: `gmail.readonly` + `gmail.labels` (labels.create/delete; settings.basic does not cover it) + `gmail.settings.basic` (filters.create/delete). A grant missing any of the three is refused (`scope_missing`) before anything is written. This is a broader consent than reading mail and needs its own user-facing consent preview before any other user connects.
- Query: the one tested on the OTPanda development mailbox, 10 live arrivals: 5 of 6 OTPs labeled, a bare-number message missed, 0 of 4 negatives labeled. That is not general accuracy: any code mail the query does not match is never collected in this mode.
- Label name `OTPanda codes` was chosen here, not by the experiment.
- Arrival: history is requested with `messageAdded` and `labelAdded` on the label. A message can appear as added with the label, or as the label added later by the filter. `labelsAdded` entries count only when they include THIS connection's label; both sightings resolve to one message id and the handled-dedupe makes the second free. The live arrival sequence for filtered mail still has to be confirmed against real Gmail (the tests use a fake).
- Ownership: nothing is adopted. A label that already has the name fails the connect (`label_exists`). Provider ids of the one label and filter this app created are stored (`label_id`, `filter_id`) and are the only things ever deleted.
- Partial failure: if the filter, the watch or the guarded write fails (including a revoked session or a mailbox owned by another account, which is checked before any write), whatever this call created is deleted. Reconnect never reuses earlier artifacts: it deletes the stored label and filter ids (a 404 is fine) and creates new ones, so there is a brief window with no filter during the replace. If creation fails after the old label was removed, what this call created is deleted and a still-active row is marked `reauth_required` (only if it still holds the old label id).
- Lifecycle single-flight (DEV ONLY, `gmail_op`): label mode requires `devMailbox` on the OAuth service (the one allowed mailbox, canonical form) and refuses without it (`dev_mailbox_required`). Connect, disconnect and watch renewal each insert one `gmail_op` row for the mailbox before their first Google call (callback: before the code exchange) and delete it only when every mutating call (label/filter create or delete, watch) got a definite answer. A timeout, transport error, a 2xx whose body cannot be parsed or lacks the expected id (label, filter or watch: the write happened but we cannot name it), or a 408/429/5xx answer to a mutating call marks the row `indeterminate` and keeps it; a crash leaves it `running`. There is no expiry and no takeover. While a row exists, connect returns `lifecycle_blocked` before any exchange, renewal skips the mailbox (`lastRenewal.blocked`), and disconnect returns `lifecycleBlocked` (an in-flight operation: nothing changes, retry) or, when the earlier operation is `indeterminate`, still does the local revoke so collection stops but touches nothing at Google (ids stay and show as left over). The row stores the starting `owner_id`; the status response carries `lifecycleBlocked` for that owner only (also when a first connect never produced a connection row). Clearing a row is an operator step that needs a definite answer about the earlier request; looking at the mailbox does not prove a late write cannot land. A callback for another mailbox is refused after the profile call with no Gmail write (`mailbox_not_allowed`). Exchange failures are treated as definite: no state is stored and nothing at Gmail was written, but a grant may exist at Google that we never saw. Non-dev mailboxes are not supported by this protocol. Generation compare-and-set (`gmail_connections.gen`, bumped by every connect and by the source-revoke trigger, i.e. any revoke path including the generic one): a connect writes only if the row still has the generation it read, so a revoke or owner disconnect landing while it prepares its write is never undone; the connect returns `source_changed`, writes nothing, removes what it created, and the user retries deliberately.
- Disconnect (mounted route): `disconnectGmailGuarded(db,user,sourceId,now,{sync})` hands its session-guarded revoke to `sync.disconnect(owner,source,{revoke})` as the local step. In label mode, inside the single-flight: re-read the row, fetch one access token (only when ids are stored), run the guarded revoke, delete the stored ids, clear them by compare-and-set. If the guard refuses, nothing is deleted at Google (a token refresh may already have happened). The Google grant is NOT revoked: the app stays in the user's Google account permissions until they remove it there. Results carry `remoteRevoked:false` and `googlePermissionRemains:true`.
- Disconnect (general): same, without the session guard. Without label mode nothing is sent to Google at all. A Google failure on a delete still disconnects locally and is reported as left over.
- Still no polling: delivery stays push driven.

## Dev-only scheduled maintenance (`src/gmail-dev-maintenance.js`)
`runGmailDevMaintenance({sync,store,budget,clock,mailbox,tasks})` is a function over built services; the mounted dev host calls it from its scheduled handler (this change mounts nothing and adds no cron). `mailbox` is required (the one allowed dev mailbox); without it the call throws. Tasks: `retries` (due deferred fetches, SQL-scoped to the mailbox, max 5), `renew` (watches expiring within 2 days, SQL-scoped, through the single-flight so blocked/indeterminate operations skip it and count in `renewal.blocked`), `prune` (expired OAuth states, 100 rows). It selects only due rows and never lists or polls an inbox: with nothing due it makes no Google call and about three D1 queries. Tasks are isolated; the result has counts only. Suggested split on the free plan (each invocation has its own 50 subrequests): `*/5` runs retries+renew, `*/15` runs prune. Without this wiring the dev watch expires about 7 days after connect and push stops silently (watch_expires_at stays visible in the DB).

## Source review notes (port onto API main)
- Callback path is `/sources/gmail/oauth/callback`, matching the live app bridge, which rejects any other `redirect_uri`. The Google OAuth client's authorized redirect URI must be this exact value (not verified from here; a registration change is out of scope for this source delta). The callback always answers 303 to the app Sources route and shows no result there: the app route parser treats extra characters after `#/sources` as unknown and falls back to Codes, so the server does not append a result. The Sources list and status are the visible outcome. A neutral connected/failed marker needs an app-side change first.
- The refresh cookie is `SameSite=Lax; Secure; HttpOnly; Path=/`. Lax cookies are sent on the top-level GET navigation back from Google, so `inspectBrowserRefresh` can read it. Not exercised against a real browser or Google redirect.
- Composition is DEV ONLY and label mode only. `createGmailSourceServices` requires the non-secret var `GMAIL_DEV_MAILBOX` (no default), passes `labelFilter` and `devMailbox`, and is not built without it, so it never falls back to INBOX mode. The three-scope request matches the app bridge. Scheduled work runs only through `runGmailDevMaintenance` for that mailbox and returns counts only.
- Migration 0051 depends on `sources(owner_id, source_id)`, which `UNIQUE(owner_id, source_id)` in migration 0003 backs with an index.
- Disconnect begin checks that the owner holds that Gmail source before a step-up challenge is issued.
- A disconnected mailbox row keeps `mailbox UNIQUE`, so the same mailbox cannot be connected by a different owner while a row exists. Reconnect by the same owner relies on the lifecycle generation. A real ownership transfer needs an explicit operator step.
- Extraction bound: `extractEmailCode` ignores any text longer than 100000 characters (returns no code), so oversized bodies are not scanned.
