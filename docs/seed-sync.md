# Inactive native seed sync (server)

Flag default OFF, nothing mounted (`createSeedSyncHttp({enabled:false})` is a 404 before any limiter, D1 or key access). Own entries only, android sessions only, download only, synthetic data only. Not activated, no real keys.

## Pieces
- Migration 0052: `totp_seeds.seed_version` (backfill 1) plus non-secret `algorithm/digits/period/seed_bytes`; `seed_sync_owner` revision; `seed_sync_tombstones`; `seed_sync_keys` (one row is one enrollment); `seed_sync_challenges`; `seed_sync_events` (audit; route to the existing security log when mounting).
- Triggers on `totp_seeds` bump `seed_version` and the owner revision (and write tombstones) inside the writing statement, so every route that changes a secret does it atomically. They skip account-deletion cascades.
- ROLLOUT ORDER: D1 counts trigger rows in `meta.changes`. Deploy the count-compatible code (this patch changes `totp-seeds.js` and `totp-management-http.js` to `>= 1`) BEFORE applying 0052. Do not roll back to pre-patch code after 0052.
- `src/seed-sync-proof.js` (three purposes), `seed-sync-seal.js` (ECDH P-256, HKDF-SHA256, AES-256-GCM), `seed-sync.js` (service), `seed-sync-http.js` (routes), `test/seed-sync-vector.json` (shared synthetic vector; regenerate with `node tool/seed-sync-vector-gen.mjs`).

## Rules enforced
- Enrollment needs a fresh action-bound passkey step-up proof (action digest commits to owner, install, the new key's public JWK and the security generation) and the new key's signature over a one-use challenge. Same public key is never re-enrolled. A new enrollment for the same install supersedes the old key in the same batch. One active key per (owner, install) by partial unique index; 20 active keys per owner; 32 outstanding enroll challenges per owner; 8 per key.
- `installId` is a client-generated stable per-install random id. device_sessions ids change on every sign-in, so they cannot be used. A reinstall or cleared data makes a new install id, so the old row stays active until remote revoke or generation bump; at the 20-key cap new enrollments are refused (no silent eviction). This needs a settings revoke surface.
- Challenge expiry is the server's stored value: the signed message is rebuilt from the stored row, so a client cannot choose or extend it. A challenge is consumed atomically (UPDATE ... WHERE used_at IS NULL ... RETURNING) for the same owner, session device and purpose BEFORE any decrypt or seal. A bad signature burns it.
- Begin is opaque about key state. Only a request whose signature verified can get `key-revoked` or `generation-changed` (per request, joined to the current account generation); everything else is 409 `unavailable`.
- Snapshot reads revision and entries in one statement. No secrets. Absence in a complete snapshot means removal. `complete=false` when over SNAPSHOT_CAP (1000), with no removals applied; there is NO paging in v1 (a cursor would need a new signed field or its own purpose). Entries with NULL metadata (pre-migration rows) are `unsupported/metadata_pending` until `SeedSync.backfillMetadata()` runs (bounded, decrypts in memory). Snapshot response includes `maxBatch` (3, pending CPU qualification).
- Batch seals each seed to the client's ephemeral key. Version and envelope are read in one query, revalidated after decrypt, and key and generation are rechecked before release. Per-entry status: `sealed | stale | removed | unsupported`. Plaintext is the seed only; the server sends no AAD. Server memory zeroing is best effort only.
- Sealing does not defend against a compromised server (it holds the seeds), and the server is not authenticated beyond TLS. State that in user-facing scope.

## Review additions (v5)
- `seed_version` is the owner revision after each change (strictly monotonic per owner), so delete then re-create of the same entry id, and the first change to a pre-migration row, always produce a larger version. Metadata backfill also moves the owner revision (trigger). Run `SeedSync.backfillMetadata()` repeatedly until `metadataPending()` is 0 BEFORE mounting; nothing schedules it.
- Revoke authority (reuses the EXISTING remote sign-out verification; no policy change). (i) Own install, online sign-out or disable: `revoke-begin {keyId}` then `revoke-finish {token,signature}`; the signature is by the key itself over purpose `seed-sync-revoke` (fields ownerId,keyId,deviceId,generation,challenge,expiresAt; same label/field style, one-use server challenge, expiry from the row), with the caller's live android session. The reason is always `disabled`, derived from the path; the client chooses nothing. Offline: local erase proceeds and the server row stays until another path revokes it. (ii) Another install's key: no seed-sync route. The existing remote session revoke (second-device approval via `consumeChange`, and the passkey step-up `apply`, plus google-unlink) now also revokes, in the same batch and under the same guards, the seed-sync keys whose `last_device_id` is the revoked session's device id (reason `remote`). `last_device_id` is set at enroll and on every verified signed finish. `list {}` shows keyId, installId, createdAt, lastUsedAt, revokedAt, reason (installId is not secret and authenticates nothing).
- Sessions and keys: ordinary expiry, refresh and re-login do NOT revoke a key (once per device). An explicit remote sign-out DOES revoke the keys last used from that session; the device then gets `key-revoked` after its next signed request and purges. Limits, to disclose: a device that never contacts the server keeps its local keys until it reconnects; and if a device signed in again (new device id) but has not yet made a signed seed-sync request, remote sign-out of that new session does not reach its key (it is linked only by last use). The server emits only key-revoked and generation-changed, never session-revoked or device-revoked, so a client treats a bare 401 as suspend. Deploy order: migration 0052 first, then the recovery-controls change, since that code writes to seed_sync_keys.
- Release guard re-checks key, generation AND the caller's live session before releasing a snapshot or sealed batch. If the session ended mid-read the answer is opaque (no purge code).
- Per-key pull limit: 12 begins per minute per (purpose, key), on top of the per-owner and per-address limits.
- Enroll begin issues a challenge before the 20-key cap is checked; the cap is enforced at finish (late failure).

## Review additions (v7)
- Definitive key status without a session (offline-key revocation learned on reconnect). General native renewal is NOT changed (it stays generic 401 for revoked, expired and unknown). A remotely signed-out device has no live session, so it asks the key itself: `POST status-begin {keyId}` (no bearer, no Origin) returns one shape for every input: `{token,challenge:{keyId,challenge,expiresAt}}` (unknown, revoked, rate-limited and missing rows look the same; only an existing key gets a stored one-use challenge). Then `status-finish {token,signature}`: the signature is by the enrolled key over purpose `seed-sync-status`, fields keyId,challenge,expiresAt (same label/field style; vector included). The challenge is spent atomically first; only after the signature verified does the server answer `{state:'active'|'key-revoked'|'generation-changed'}` (200). Everything else (unknown key, expired, bad signature, wrong purpose, replay, missing row) is the same opaque 409 and MUST NOT purge. It grants no access and returns no seeds, never touches last_used_at. Limits: per address 30/min, per key 12/min, max 8 outstanding challenges per key. Purge only on `key-revoked` or `generation-changed`; client calls it on reconnect when a signed seed-sync request is not possible (no live session) and after a bare 401 on renewal.
- Retention: key rows are the status source, not session rows. Device-session cleanup deletes revoked/expired sessions; seed_sync_keys rows are untouched by it (tested after deleting every session row). Revoked key rows are retained until the account is deleted (FK cascade); no pruning is implemented. Any future pruning must keep revoked rows for at least 400 days, because an offline device may reconnect much later; a missing row stays non-purging, and a missing row never means revoked.
- last_device_id link is one statement guarded by the live android session predicate at the commit; a session revoked between claim and link fails the finish (opaque) and nothing is released (tested with the revoke injected at the link statement). A client MUST run the signed snapshot (sync start) before any other seed-sync work after sign-in, so the key is linked to the new session within seconds; the residual window (re-login, then remote sign-out of the new session before that first signed request) is that short window and is disclosed, not a user choice. A later hardening may store install_id on device_sessions.
- google-unlink covers keys whose last_device_id belongs to sessions revoked at exactly the batch time for the removed identity; a session of that identity revoked earlier is not covered.
- Deployment is three commits: (1) count-compatible totp seed writers, `>= 1` (no schema dependency); (2) migration 0052 and guard test; (3) service, routes, recovery-controls link, tests. Order 1, 2, 3. Rollback from 3 to 2 is safe (2 has no code that needs the new table, so remote sign-out keeps working); never roll back below 1 after 0052. Pre-patch code against 0052 fails 15 extra tests (exact-count guard), and stage 3 recovery-controls without 0052 fails: both are ordering negative controls.

## Status proof: limits and client rules (v8)
- Purpose binding: every finish consumes only challenges of its own purpose (enroll, snapshot, batch, revoke, status), and the four session finishes also bind the session's device id. Tests cover a status token refused by the four other finishes and their tokens refused by status-finish (with valid signatures of the status purpose and of each other purpose), plus a mutation (dropping the purpose filter from the status consume makes a test fail).
- Availability exposure: key ids are random UUIDs and not secret once an app knows them, so someone who knows one can fill its 8 outstanding status challenges or its 12/min limit. The real begin then gets the same-shape fake and finish is the opaque 409, so revocation is not learned while that lasts (fails closed, never reads as active). It recovers when the challenges expire (TTL 120 s) and the minute window passes (tested). The client MUST treat a fake or failed answer (409, 429, 503, network error, timeout, malformed or oversized body, unknown state, "active") as retry with backoff and never as a purge, and purge only on HTTP 200 with a body that is exactly `{state}` where state is `key-revoked` or `generation-changed`. The answer is not signed (TLS is its only authentication), so the client uses a size cap and an exact parse. The 30/min per-address limit is shared by all seed-sync routes behind one NAT address, so a failed status is a retry too. Do not purge on any other generation signal.
- Timing: the response SHAPE is equal for every input; the TIMING is not hidden (a real begin does a lookup, a rate-limit write, a sweep and an insert; a fake does none). Key ids are unguessable, so this is an accepted low risk, not a guarantee.
- Account deletion: key rows are removed with the account (ON DELETE CASCADE on seed_sync_keys; there is no revoke or tombstone step, and no code revokes first; tested). After deletion a missing row is non-purging, so a device that never reconnected before deletion keeps its offline keys on that device indefinitely. This is the disclosed fail-closed limit: the server cannot say anything about a key it no longer has, and the device has no seeds to refresh anyway. Deleting the account does not reach the local copy.

## Audit and new-device notice (v9)
- Audit: `seed_sync_events` (enrolled, revoked, denied with reason) is the audit trail; there is no existing security-log table to route into (the only security notice mechanism is recovery_notifications, which is bound to email recovery requests by FK and a kind CHECK, so it is not reused).
- New-device notice: migration 0053 adds `seed_sync_notices` (stage 4, table only). Stage 5 inserts one `enrolled` row in the SAME D1 batch as the key insert at enroll finish (guarded on the key row existing, so a refused enrollment writes none). `deliverSeedSyncNotices({db,deliver})` has the recovery-notifier contract: 60 s lease, at most 5 attempts with backoff, terminal `failed_at`, recipient always the stored account mailbox, fixed template (`seed-sync-enrolled`) with no key id, install id or other detail. The recovery mail transport accepts that kind. Recipient rule is the existing notifier's exactly (`account_emails.email` for the owner; that table has no unverified rows, `verified_at` is NOT NULL by schema and a test pins that; the query also states `verified_at IS NOT NULL` as defense in depth). Never silent: if the failure-path write itself fails the row can sit at attempts=5 with no `failed_at`; every run first marks such rows failed (`healed`), and `seedSyncNoticeHealth({db})` is the monitoring read: `failed` (terminal rows), `exhaustedUnmarked` (attempts>=5, no failed_at, no delivered_at), `overdue` (pending and untouched for 15 minutes, which also catches a deliverer that is not running or a stuck lease) and `oldestPendingAgeMs`; `alert` is true when any of the three counts is above zero. Delivered rows are pruned after 30 days (50 per run); failed rows are kept for operators. Wording: the notice says to sign the device out from another passkey-signed-in device (the existing remote sign-out, whose revoke policy is unchanged) and that codes the device already holds stay on it. It does not promise a local disable or a remote wipe. It is NOT wired into any worker or schedule yet. Activation gate: (1) a scheduled invocation of deliverSeedSyncNotices (every few minutes, bounded limit), (2) an alert on `seedSyncNoticeHealth().alert` that reaches the owner of the deployment, (3) a test of that alert path. The wiring and the alert are not built here.
- Order: 1 compat code, 2 migration 0052, 3 service, 4 migration 0053, 5 enroll-notice code. Stage 5 code on a database without 0053 fails every enroll finish (opaque), so 0053 must be applied first.
