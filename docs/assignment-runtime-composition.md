# Assignment runtime composition, inactive candidate

The inactive browser identity runtime composes only begin/finish/status assignment POST endpoints. The Cloudflare bootstrap, Wrangler entrypoint and production activation flags are unchanged. Merged internal code is not a usable live mutation route.

Exact API and app origins, strict methods, pure preflight, owner/device access and streamed body guards remain layered. Assignment preflight permits Authorization and Content-Type and needs no environment, ingress resolver, provider counter, D1 or key import. Query-bearing assignment paths are refused at the edge. Begin and finish share the existing tighter authentication provider counter; status uses the read counter. No new binding, paid service or counter capacity is introduced. These approximate edge limits are not financial caps and post-auth D1 limits remain necessary.

Assignment key access uses the same cached code-key import as encrypted reads. After owner authorization and target context checks, begin verifies readiness before inserting an intent or ceremony, so missing keys give503 before the user gesture. Status stays keyless and available during key failure. Unauthorized requests never import keys. Finish retains guarded encryption and cannot assign with unavailable keys. Key failures stay cached within the isolate. Existing login/session issuance, rotation and recovery algorithms remain unchanged.

Browser integration must show the returned target identity, active recipients, automation recipients and irreversible-release warning before a user gesture invokes the passkey. Refused or lost finish is an unknown outcome, not definite failure. Reconcile the same owner/device intent status with bounded backoff. Do not retry the mutation automatically, issue a replacement intent while the original may be in flight, or show failure merely because a duplicate lost the ceremony claim. Assigned is confirmed only by finish/status; pending remains pending, expired or missing after transport loss still cannot prove no effect if result retention elapsed or access was revoked. Explicitly let the user reauthenticate/review current entry state when reconciliation cannot establish the outcome.

Tests cover composed cryptographic begin/finish/status and idempotent finish; lazy key access; keyless status and missing-key begin with zero intent/ceremony inserts; pure edge preflight and exact path/method/origin/query policy; auth versus read budget selection. Local D1 execution is separate from actual Worker-isolate/browser/hardware proof. Remote production D1, real browser WebAuthn/clock behavior and actual accounts remain unverified. No production activation is part of this increment.

## Definitive negative outcome revision

Migration0020 adds a retained `retired_at` state to assignment intents. Only the actual ceremony claimant retires failed finishes, with an update guarded against consumed intents. Status reports `not-assigned` only from this durable state, never from absence or a standalone clock comparison. At expiry, status first performs a session-bound guarded retirement update. The final assignment batch requires `retired_at IS NULL`, so expiry retirement and commit serialize: commit first yields assigned, retirement first prevents any stale-time/in-flight commit. Legacy expired, missing/unauthorized/cleanup-unavailable status is not a negative receipt. Retired rows retain the existing ten-minute result TTL and do not consume the pending cap. Unissued begin failures alone can delete their rows.

Status now includes a guarded D1 UPDATE even before expiry (a no-op in that case), followed by its read. It stays keyless and within existing status budgets. This is an operational change, not a claim that status is database read-only. No route/bootstrap activation is included.
