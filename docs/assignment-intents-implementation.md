# Assignment-only action intents, unmounted candidate

This increment adds internal assignment orchestration and a separate, unmounted HTTP adapter. It changes neither production routes nor current login/session/recovery algorithms. No real source is enrolled, read or assigned. Google-only action proof remains unsupported, with no email-only or legacy bypass.

Begin derives the exact assignment from owner-private unassigned event, owned target and current share count. The immutable intent binds owner, stable device ID, generation, source/event/target, exact old ciphertext hash, event lifetime, explicit entry/share revision and server-produced digest. Summary states active recipient and automation-enabled recipient counts, and explicitly marks release as irreversible. The canonical action binds these counts and the irreversible flag. Existing label/account-name metadata rules are unchanged. Entry label/account/service and all share insert/update/delete changes increment the revision, including add-then-revoke ABA changes. Failed ceremony creation retires its pending intent. A finish retires an uncommitted intent only if that caller actually claimed the one-use ceremony, including later exceptions. A competing failed claim cannot delete an in-flight winner. Committed receipts are retained. Five pending intents per owner, two-minute proof lifetime, bounded cleanup and address/owner request limits bound writes. Status receipts expire after ten minutes.

Step-up uses the existing cryptographic passkey verifier with UV required. Step-up challenge derivation additionally domain-separates and hashes random entropy plus exact action. Login challenges/tokens remain separate. The HTTP adapter accepts only exact-origin bearer-authenticated POST application/json (optional UTF-8 charset) with bounded streamed body and exact allowed fields. Browser caller cannot supply owner/device/generation. Public deployment and adapter composition remain unchanged; production edge-limit composition and browser confirmation UI need a separate reviewed integration.

Finish verifies action hash and purpose-bound WebAuthn proof, decrypts the original unassigned envelope and reencrypts it for the selected entry. A D1 batch conditionally consumes the intent only under fresh session/generation/credential/source/event/expiry/target-revision predicates, writes the exact event only when the first statement changed one row, then inserts a CHECK-constrained receipt requiring exactly one assignment change. The receipt constraint rolls back all batch writes if assignment was unexpectedly ignored. The finish adapter preserves a committed result even if a session is revoked immediately afterward. Revocation before commit still wins through SQL predicates. A lost response followed by revoked-session status remains unknown to that caller, never a promise of no effect. Lost-response retries resolve owner/session-bound assigned status; they do not assign again. Credential signature-counter changes can occur before a failed assignment, which is expected and does not consume a source code.

The server cannot trust a compromised app origin to show the actual summary. WebAuthn does not display a transaction. This protects action authorization from stolen bearer-only callers, not XSS or a hostile Pages deployment. Assigning to a shared target intentionally exposes its current code to active recipients only after the user sees recipient and automation counts and confirms the actual server summary and irreversible disclosure. Revoking later cannot undo a recipient reading the code. A share-state change invalidates the proof.

Evidence: cryptographic Node tests cover success/decryption, purpose/action tamper, one-winner concurrency, session/source/security-generation/expiry/envelope/target/share invalidation, bounded writes, owner/session status, HTTP boundaries, revocation during encryption and transaction rollback. `node tool/assignment-d1-check.mjs` repeats actual migrations and cryptographic concurrent assignment against local workerd D1, then forces assignment-ignore with a trigger and proves receipt CHECK rolls back intent consumption/event mutation. No hardware WebAuthn, production mutation or complete browser integration is claimed.
